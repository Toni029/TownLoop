# Planned read-only cleanup quota gateway

Local preparation only. No IAM grants, account creation, deployment, endpoint metadata lookup or environment configuration has been performed.

`previewDatabaseCleanup` keeps the existing native callable name and accepts only `preview`, known categories, an optional bounded cursor, and the existing UI request ID. It verifies the Firebase ID token with revocation checks, rechecks canonical approved **Admin** status and the account revocation fence, then writes only an `adminRead` budget in `safety_limits/{uid}`. The shared policy permits 12 preview requests per minute and 1,000 per day, including pagination/refresh. It creates no cleanup job and imports no destructive cleanup engine. The private inventory repeats the original strict authorization and read-only behavior.

The public gateway uses the planned dedicated identity `townloop-request-controls@cc-livingcommunity-app.iam.gserviceaccount.com`. The inventory retains `townloop-cleanup-preview@cc-livingcommunity-app.iam.gserviceaccount.com` and its existing read-only Firestore/Storage IAM. **Do not add write permissions to the inventory identity.** The gateway needs canonical user/revocation reads and transactional quota get/create/update permissions; its source confines writes to quota state. Firestore IAM does not itself supply document-path authorization equivalent to Security Rules, so review the dedicated gateway's permissions and source together. Do not grant it cleanup/deletion/Storage mutation privileges.

The new private callable export is `readOnlyDatabaseCleanupInventory`. Its adapter uses the original local read-only entry unchanged, applying a checked source transformation that changes only the export name and adds the single gateway invoker. The original implementation and authorization logic are not copied into a second maintained implementation. Scoped packaging must include both original read-only files, the private adapter, the gateway entry/pure module, and shared quota policy/helpers. The wrapper fails if its source anchor changes. Keep the two runtime identities distinct.

For a future approved rollout:

1. Provision/review the dedicated gateway identity and least required quota/read permissions; grant it invocation of **only** the private inventory Cloud Run service. Deployment tooling also requires the separately reviewed ability to deploy/act as these runtime identities. No such grants are included here.
2. Deploy the private inventory first with only the gateway identity as its invoker. Verify both Cloud Functions/Cloud Run metadata and IAM in project `cc-livingcommunity-app`, region `us-central1`; remove `allUsers` and other public invokers from the private service. Verify its runtime identity still lacks writes/deletes and test that an end-user token alone cannot invoke it.
3. Read the private service's actual **Cloud Run service URI** from that deployment's metadata. Set the gateway's server-only `CLEANUP_INVENTORY_SERVICE_URL` to that verified URI. The code accepts the expected inventory service name on `run.app`; the deterministic form pins project number `883715389126` and region `us-central1`. A legacy hashed `-uc.a.run.app` URI must be checked against the trusted deployment metadata because the hostname does not encode a verifiable project number. Missing/malformed config fails before quota charging. Do not use the `cloudfunctions.net` alias as the Google OIDC audience, and never accept a URL from a client request.
4. Deploy the gateway at the existing `previewDatabaseCleanup` callable name, replacing the old publicly reachable inventory implementation as part of the coordinated cutover. Do not leave an additional public inventory alias that bypasses quota. Keep the inventory IAM private throughout. Verify the old callable now reaches the gateway identity and durable limit.
5. Test valid/pending/revoked/disabled accounts, every role, pagination, distributed quota exhaustion, private service failure, and read-only IAM. Rollback must preserve private inventory IAM or explicitly account for restoring the quota bypass; never grant deletion capability or use permissive database rules as a fallback.

The gateway obtains a Google OIDC token using `GoogleAuth.getIdTokenClient(verifiedServiceUri)` and sends it as `X-Serverless-Authorization`. It separately forwards the already verified end-user Firebase token as `Authorization` for the unchanged callable's canonical authorization. No tokens are stored in quota records, request URLs or logs. Custom App Check enforcement remains off.

`google-auth-library` version **10.9.1** was already present in the Functions lockfile/install tree. It is promoted to an explicit dependency at that same exact version; only the root dependency declarations changed. No install or dependency-tree change was performed.

Local tests: `node --test functions/databaseCleanupQuotaGateway.test.cjs functions/databaseCleanupReadOnly.test.cjs`. These use synthetic identities, records and transport boundaries. Actual private IAM invocation, service URI/audience behavior and deployed permission separation remain unverified until a separately approved deployment.
