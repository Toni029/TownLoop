Account and community information

Email/password and, where enabled, Google sign-in use Firebase Authentication. The current native Google option remains unavailable until its configuration is verified. Resident profiles in Cloud Firestore include name, email, resident address, optional phone and emergency-contact details, profile image, account approval and role, and the terms version and acceptance timestamp. Only provide another person's contact details when you have permission.

Community features store posts, comments, marketplace listings, reactions, activity participation, maintenance requests and status updates, and conversations in Firestore. Selected photos, videos, profile images, and newsletter documents may be uploaded to Firebase Storage. These records support the features you choose, community administration, and access controls. Community content is visible to its intended community audience; maintenance staff and authorized office administrators access records needed for their work. Messages are available to their participants through the service. Do not assume messages are end-to-end encrypted.

Medication and other device storage

The newly prepared native implementation keeps medication and task reminder names, schedules, quantities, and taken status on the device, keyed by the signed-in user. A new app binary containing Expo SecureStore can use protected device storage and migrate existing AsyncStorage records after validating and verifying the protected copy. Older app binaries without that native capability continue to use AsyncStorage; an over-the-air JavaScript update alone does not add the protection. The baseline implementation used AsyncStorage. Ordinary sign-out preserves local reminder records. The owner must verify the released binary, migration, device backup behavior, and explicit deletion path before claiming these protections for installed apps.

The newly prepared web medication implementation persists records separately by user ID in browser IndexedDB, encrypted with AES-GCM using a nonextractable browser cryptographic key stored with the encrypted records. Refreshing the page retains saved records. This browser at-rest protection is not a private vault: scripts running with the site's origin can use the key, and clearing site data or browser storage eviction can remove records. Older web versions saved medication records in plaintext browser localStorage. Explicit copying of those legacy records requires a verified durable write; the original legacy copy remains until separately removed with confirmation. The owner must verify this prepared storage implementation in the released browser version.

These reviewed reminder stores do not contain a cloud-sync operation and are not a medical record service. Information you enter in a post, message, attachment, or maintenance request may be uploaded even if it mentions health or medication. Review all distributed versions and device backup behavior before making a local-only data claim.

Translation, AI, and external services

When maintenance translation is requested, request titles, descriptions/notes, and comments can be sent through the TownLoop translation service to Google Translate or a Gemini fallback. When an authorized editor requests newsletter analysis, PDF content is sent through the TownLoop server to Google Gemini for extraction. AI output can be inaccurate and requires human review. Avoid submitting unnecessary sensitive information. Provider retention, model-training settings, processing locations, and contractual terms have not yet been approved for this release; no promise of zero retention or exclusion from training is made here.

Firebase supplies authentication, cloud database and file services. Expo's update service checks for and delivers app updates. The weather tile queries Open-Meteo for configured community coordinates, rather than requesting your device GPS location. External services receive network requests and may process connection or technical information. The exact production SDK, server, hosting, and update-service logging inventory remains a release-review item. This draft does not assert that no technical data is collected or that data is sold or used for advertising.

Permissions and security

The app asks for camera access when you choose to take an attachment photo and uses the system photo/video picker for selected media. Features can be limited if you decline access. Final Android permissions must be verified from the release manifest. TownLoop uses authenticated Firebase access controls and HTTPS service endpoints; these measures do not guarantee complete security. Device/browser storage is not described as an encrypted health-data vault.

Retention and account deletion

Submitting an account deletion request does not delete or disable an account. A verified resident requests deletion through Edit Profile or the public request page. Admin/VIP must review it; no one can approve their own request. Review targets 3 business days (Monday–Friday in America/New_York), and unresolved reviews escalate after 7 calendar days to authorized Admin accounts only. VIP retains review permissions but receives no automatic escalation notifications. Scheduled monitoring is prepared but remains disabled. A rejection requires documented requester withdrawal; a legal/security delay requires a documented case and finite review date. A delay does not restart the original deadlines.

After independent approval, personal-data deletion targets completion within 7 calendar days. Firebase Auth, private profiles, resident-owned posts/listings and authored comments are removed under the approved policy. Necessary maintenance history is reduced to nonidentifying operational fields; shared conversations redact the departing resident's identity and authored messages while preserving the other participants' access. Ambiguous identities, unknown free-text references and unverified media links require review rather than guessed ownership. These blockers remain visible and must not be marked complete.

Ordinary retained-record redaction/deletion and account-linked audit receipts expire within 60 calendar days from the original request. Necessary legal/security exceptions require specific justification and documented expiry; this implementation does not authorize indefinite holds or silently extend retention. The six unresolved, quarantined legacy attachments remain excluded from deletion until independently resolved. Their preservation is an explicit outstanding exception requiring status resolution, not a promise that their ownership is known.

Account-specific native medications/checklists and caches are removed when an online client receives authoritative deletion confirmation, including protected storage where available. An offline device, stale/revoked session without deletion proof, older browser storage without a proven account owner, and backups cannot be erased remotely by this app. Ordinary sign-out and transient connection errors do not erase local records. All backup configuration changes are deferred. Existing recovery settings remain unchanged; application record deletion alone does not purge backups. Verified retention is described below.

The policy and processing code are prepared locally. Workers remain disabled pending safe deployment, verified media compatibility, resolution of legacy/cross-database scope, and operational staffing. These disclosures describe the intended approved workflow and its current implementation limits; they do not assert that deletion is already active on the hosted service. Support email monitoring, any required legal operator details and the policy effective date still require confirmation before publication.

Verified retention and operational status — draft disclosure

As of October 25, 2026, verified deletion requests and independent review are deployed; approval records a held decision and does not authorize deletion. Automatic processing and cleanup remain disabled. This is not a claim that deletion obligations are satisfied by recording a request: a staffed, verified processing path must operate before public release. Sixty days is TownLoop's approved maximum ordinary retention window, not permission to postpone routine deletion for sixty days.

Read-only configuration checks found no managed Firestore backups or backup schedules, and point-in-time recovery is disabled in both known databases. Firestore reports a one-hour version-retention window. The restricted release-backup bucket has an age-60-day expiry rule and soft deletion disabled; lifecycle execution is asynchronous, and this does not prove every historical copy is absent. Application Storage retains soft-deleted objects for seven days. General provider logs currently use thirty days; Google’s existing system-required audit bucket uses a fixed four-hundred-day period. This is a provider setting, not an established legal obligation applying to TownLoop or permission to retain application records longer. No specific applicable legal basis has been established for a TownLoop 400-day exception; owner/legal review is required. Application audit receipts keep the 60-day maximum. Resident message bodies, photos and unrelated personal information must not be copied to audit receipts. No resident log contents were examined; log field minimization and actual access remain to be verified without reading resident content.

Six unresolved legacy attachments remain quarantined from ordinary SDK access and excluded from automatic cleanup until independently resolved. Their existing bearer download links have not been revoked; possession of such a link may still allow access. Quarantine and authenticated app reads do not make these old links private. Other unsupported identity or media relationships remain review items rather than guessed ownership.

Prepared Android cleanup clears only the affected account's reminders and app-owned media cache after authoritative deletion/disable evidence, with protected retry state after interrupted cleanup. An offline phone cannot learn a new server decision until it reconnects. Revocation without a usable deletion signal, historical unassigned caches, and the unchanged hosted website remain limits; no remote erasure from an offline device is promised.

The prepared cleanup protocol uses a cleanup-only device credential in protected native storage and a server-side credential hash. It can confirm deletion, disablement or revocation after sign-out without granting account access or permission to delete an account. Credentials have finite expiry of no more than 60 days, capped by the original deletion-request deadline once processing starts. This protocol is inactive pending coordinated release. An unenrolled device or a device returning after proof expiry may not have usable server evidence; no remote erasure of permanently offline devices is promised. Cleanup remains account-specific.
