# Play messaging regression correction — 2026-11-09

Local implementation only. No deployment, credential association, notification sends, resident writes, rules change, or build was performed.

## Evidence and confirmed causes

Read-only inspection targeted `cc-livingcommunity-app` default database, deployed function metadata/source and EAS Android credentials. Private snapshots are outside Git in `~/.local/state/townloop/messaging-push-2026-11-09`. Cloud Logging returned HTTP 429; no repeated logging queries were made. Findings are based on deployed source, live document shapes, credential metadata and delivery receipts, not a reconstructed per-request log trace.

- **Private HTTP 400:** deployed `upgradeLegacy` applies the Firebase UID regex to a Firestore document ID. Three of four identity-v2 private records have email-shaped IDs containing `@`/`.`. Verified participant UIDs are valid. New compose auto-upgrades a matching legacy record and rejects its document ID. The correction allows valid single Firestore ID segments, while rejecting path traversal/control characters and preserving strict UID validation and verified-pair checks.
- **Office/Crew:** historical role-wide records lack verified per-person membership required for safe cutover. The historical-review refusal is intentional. Automatic migration prevented even starting a separate new conversation. `createFresh` explicitly creates/reuses a secure current group without copying old messages, altering the old source or inventing historical membership. Current authorized v3 conversations are preferred over legacy candidates. Native compose preserves the draft and offers this explicit recovery. Unverifiable private records remain blocked for review.
- **Marketplace/background push:** old Preview package has an EAS FCM-v1 credential association; `com.townloop.app` does not. Registration exists (five enabled Android device records; four Marketplace-enabled). Recent receipts include eight `InvalidCredentials` rejections and eighteen accepted tickets across devices. Accepted tickets alone do not prove delivery. Firestore reconnect can update the app even when push fails. The production association must be corrected separately; local code cannot repair this cloud prerequisite.
- **Discussion:** comments/replies already have descriptors and gates. Likes have no notification descriptor. Added a generic owner-only like event using the existing Discussion preference/channel. Additionally, `notifyDiscussion` has `DISCUSSION_REPLIES_ENABLED=true`, but deployed `registerInboxDevice` omits the flag and advertises replies unavailable. Restore the registration flag in the scoped release; do not change rules or silently enable user preferences.
- **Notification taps:** v3 IDs were looked up in legacy collections. Route these targets to `inbox_conversations` after notice resolution, retaining server-read rules, active-account/device binding and membership/type validation.

## Security differential review

The legacy-ID validator changes only document paths, not identity validation. Traversal, nonmember access, private `createFresh`, unauthorized Office additions and Crew rejoining are covered by regression checks. Existing authorization, membership epochs, source-hash proof, join/leave events, cleanup write barrier and read-only departed private behavior remain in place. Fresh groups use existing server transactions and authorization; they never copy old attachments/history. Existing legacy originals retain their current access policy: this correction does not strengthen or broaden their historical role-wide rules.

Likes require the actor's sole false-to-true membership-map change, a matching +1 count, unchanged comments, approved actor, published post and live owner/like verification. Existing recipient approval, blocking, category preference, sender exclusion, delivery claims and generic payloads still apply. A stable post/actor key suppresses unlike/re-like notification spam. High Android push priority is shared; sounds, icon, channel IDs and deep links remain unchanged. No new preference or schema/rules deployment is needed.
