# Category-specific retention decisions — PROPOSED, NOT APPROVED

No policy in this file is active. No live policy documents, jobs, accounts or files were read or changed. The policy templates deliberately set `ownerApproved: false`. A deployment approval alone does not approve retention or activate cleanup.

## Activation contract

- Review every collection in `functions/accountDeletionPolicy.cjs:SHARED`; add no blanket `retain` defaults to get jobs unstuck.
- `deletion_policies/account`: `ownerApproved: true`, real `approvalReference`, and each approved collection's supported action/reason. Owned Social deletion also requires a reviewed `sharedReferences` decision. Unsupported/time-based policies require an explicit implementation decision; the worker must remain held.
- `deletion_policies/media`: same approval fields; real Firestore Timestamp `trustedUploadsAfter` after stricter metadata rules are effective, plus per-category `delete_linked_media_on_parent_deletion`. A JSON string is not a Firestore Timestamp. Existing files with legacy writable metadata are never trusted merely because a migration stamps `securityVersion`.
- Do not deploy/start `resumeAccountDeletions`, `resumeMediaCleanup`, `expireMediaDrafts` or new destructive media triggers while decisions are unresolved. Do not deploy the account deletion callable before its reviewed end-to-end workflow is ready; it freezes a requesting account.
- No retention policy or media activation script is run as part of the non-destructive metadata migration bundle.
