## Decision

**Conditional public-launch readiness.** No new P0 authorization bypass or exposed server credential was found within this scope. Two P1 follow-ups remain: approved-account abuse/cost controls and the already-documented private attachment bearer-link limitation. App Check is useful additional protection, not a substitute for these controls or current authorization. Do not enable enforcement on today's binary.

Budget alerts are not hard spending caps; external provider budget/quota configuration was not verified in this pass.

## Safe App Check plan — separate approval required

1. Keep existing authorization and enforcement OFF. Verify the Play **app-signing** SHA-256 and linked Play Integrity project for `com.townloop.app`; upload-key fingerprints alone are insufficient. Preserve the old Preview registration.
2. Add native Play Integrity attestation and a Firebase JS `CustomProvider` token bridge (or a separately reviewed equivalent) rather than migrating working Firebase services. This needs a new Android AAB/native integration, not only an OTA. Retain iOS compatibility with a separately verified Apple attestation provider. Firebase's JS SDK explicitly supports React Native App Check through a custom native-attestation provider: [supported environments](https://firebase.google.com/docs/web/environments-js-sdk).
3. Cover **every** transport: Firebase JS clients, native/manual PDF REST uploads, custom newsletter/translation fetches and server REST reads forwarding a user's ID token. Enforcing Firestore/Storage without addressing those server-forwarded requests can break working Gemini verification. Custom HTTP endpoints require explicit validated `X-Firebase-AppCheck` handling; setting callable enforcement alone does not protect them. Trusted IAM task workers retain their separate service identity. See [custom backend guidance](https://firebase.google.com/docs/app-check/android/custom-resource).
4. Ship to internal testers with enforcement off; observe verified/unverified traffic and expired/revoked token behavior, reinstall/account-switch/background refresh, upload/resume and all four push categories. Use registered debug providers only in controlled development/Preview environments; never embed debug tokens in Production or weaken production attestation verdicts to accommodate old APKs.
5. Review metrics and old-client upgrade coverage before separately enabling each product's enforcement. Test Authentication, Firestore and Storage individually; apply callable/custom-HTTP checks separately. Existing clients without the bridge will be rejected. Keep a safe enforcement-disable recovery path, never a permissive-rules fallback. See [monitor first](https://firebase.google.com/docs/app-check/monitor-metrics), [Play Integrity setup](https://firebase.google.com/docs/app-check/android/play-integrity-provider), and [callable enforcement](https://firebase.google.com/docs/app-check/cloud-functions).
